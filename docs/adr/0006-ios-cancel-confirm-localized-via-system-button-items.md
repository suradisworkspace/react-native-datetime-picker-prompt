# iOS default Cancel/Done text is localized via UIBarButtonItem system items, not a translation table

The original design (docs/design/dtpicker-api.md's non-goals) deliberately shipped English-only default `cancelText`/`confirmText` on iOS, on the grounds that a hand-maintained translation table is ongoing work disconnected from the picker's core job. Android never had this gap — its native `DatePickerDialog`/`TimePickerDialog` buttons already use the OS's own localized labels automatically when we don't override them, confirmed in earlier on-device testing.

To close the iOS gap, the custom toolbar's plain `UIButton`s were replaced with a real `UIToolbar` populated with `UIBarButtonItem(barButtonSystemItem: .cancel)` and `.done` — Apple's own public, officially documented API for exactly this: a button whose title renders in the device's current language automatically, with zero translation data to write or maintain, in every language iOS itself supports. `UIToolbar.isTranslucent = false` plus an explicit `barTintColor` keep the keyboard-matched background from ADR 0005's original version.

This was chosen over a bundled translation table (ongoing maintenance, incomplete coverage — the exact problem the original non-goal was written to avoid) and over reading strings out of UIKit's own resource bundle via `Bundle(for: UIApplication.self).localizedString(forKey:value:table:)` (a long-used but undocumented community technique relying on internal key-matching that could silently stop working on a future iOS version). `UIBarButtonItem` system items carry none of that risk since they're first-class public API, not a workaround — unlike the keyboard-curve and background-color values in ADR 0005, this one isn't expected to need future upkeep.

A side effect worth noting: RTL layout (button order mirroring for Arabic, Hebrew, etc.) was already correct before this change, since the toolbar was already built with `leadingAnchor`/`trailingAnchor` constraints (auto-mirroring) rather than `left`/`right`; `UIToolbar`'s own item-array layout mirrors the same way. No RTL-specific work was needed as part of this change.

## Addendum: `cancelText`/`confirmText` removed entirely (iOS 26 / Liquid Glass)

The original design above still let callers override the default via a custom-titled `UIBarButtonItem` when `cancelText`/`confirmText` were provided. That override has since been **removed from the public API on both platforms** — `PickOptions`, the Nitro boundary, and both native implementations no longer have these fields at all.

Why: starting with iOS 26, Apple's Liquid Glass design automatically renders `UIBarButtonItem(barButtonSystemItem: .cancel/.done)` as icons (✕/✓) instead of text, with zero app-side code — but *only* when no custom title is given. A `UIBarButtonItem` with an explicit title never gets that treatment, on any iOS version, now or in the future, since icon-ification is specific to the unmodified system item. That means a caller who set `confirmText: "Submit"` would see literal text next to other now-icon-styled chrome, and whether that text showed depended on nothing but which OS version the device happened to run (identical on-device behavior *before* 26, suddenly inconsistent-looking *after*) — a real "I set X, I sometimes don't get X-the-expected-look" problem once the platform's own convention shifted. Rather than attempt to carry that override forward with some new guarantee (e.g., "if provided, always force text, forever, regardless of platform direction"), it was dropped: both platforms now unconditionally use their own OS-default button, same as Android already did. This was decided during a wider iOS UI overhaul for the Liquid Glass era (see ADR 0005's redesign section) where keeping a text-override option sat awkwardly against an otherwise icon-first toolbar anyway.

This was a clean breaking change, not a deprecation — the package was unpublished (no git tags, 404 on the npm registry) at the time, so there were no existing consumers to carry forward compatibility for.
