# minimumDate, maximumDate, defaultValue, and timezone

`PickOptions` gained four optional props: `minimumDate`, `maximumDate`, `defaultValue` (all ISO 8601 UTC strings, the same format `pick()` itself returns), and `timezone` (an IANA identifier). This reverses the original "no initial/default value parameter" non-goal now that there's a concrete need for it.

**Scoping is mode-aware.** Comparisons only look at the part of the value relevant to `mode` — date-only for `'date'`, time-of-day-only for `'time'`, full instant for `'datetime'`. Comparing a full timestamp in `'time'` mode wouldn't be meaningful: the result's date portion is always "today," so there's no stable date to compare against. Wraparound ranges (e.g. an overnight 10pm–6am window) are not supported — `minimumDate` must resolve to before-or-equal `maximumDate` under this same mode-aware comparison, or the call rejects with `E_INVALID_RANGE`.

**`timezone` makes bounds deterministic across devices.** Without it, `minimumDate`/`maximumDate`/`defaultValue` are interpreted in whichever timezone is picking right now — unavoidable, since every native date picker (`UIDatePicker`, Android's `DatePicker`/`TimePicker`) renders a calendar in local wall-clock time, not UTC. The same UTC instant can land on a different calendar day depending on the device's offset relative to whoever authored the ISO string. Passing an explicit `timezone` pins interpretation to that zone regardless of the device's own, matching how the actual timestamp is intended rather than wherever it happens to be viewed. Confirmed both are feasible natively: iOS's `UIDatePicker.timeZone` supports this directly; Android's `DatePicker`/`TimePicker` don't render anything timezone-aware at all (they're just raw Y/M/D/H/M number spinners), so it's purely a matter of which `Calendar` timezone we use to interpret the picked numbers into a final instant — no widget-level support needed.

**Invalid-input policy** mirrors the project's established pattern of surfacing real `code`s for config/programmer errors rather than silently misbehaving:
- `minimumDate > maximumDate` (mode-aware) → rejects with `E_INVALID_RANGE`, before any native dialog shows.
- An unrecognized `timezone` identifier → rejects with `E_INVALID_TIMEZONE`. Deliberately checked against the platform's actual available-IDs list rather than trusting the identifier blindly — Android's `TimeZone.getTimeZone()` in particular silently falls back to GMT for unrecognized IDs, which would otherwise hide a caller's typo.
- An unparseable `minimumDate`/`maximumDate`/`defaultValue` string also rejects with `E_INVALID_RANGE` (reusing the code rather than adding a third one — the message text distinguishes the exact problem).
- `defaultValue` falling outside `[minimumDate, maximumDate]` is **clamped** into range rather than rejected — unlike the above, this is treated as a data problem (e.g. a stale value from a backend the caller doesn't fully control), not a config error.

**Android's native `TimePicker` has no min/max-time enforcement API at all** — unlike `DatePicker`, which has native `minDate`/`maxDate`. So on Android, bounds are fully enforced for `'date'` mode, but a user can still pick an out-of-range time for `'time'` mode or the time-step of `'datetime'`; it resolves as picked, not rejected or silently corrected. iOS has no equivalent gap — confirmed empirically that `UIDatePicker.minimumDate`/`.maximumDate` are honored in `.time` mode too (the widget auto-clamps its own default value into range when "now" falls outside it, which it wouldn't do if the bounds were ignored). This asymmetry is accepted as an unavoidable platform limitation, the same way the `'datetime'`-mode partial-cancel asymmetry was accepted in ADR 0004.

**A second, separate Android timezone wrinkle**: `DatePicker.minDate`/`.maxDate` always interpret their millis value using the *device's* own default timezone to determine which calendar day it falls on — there's no public API to change that, unlike the picked-value conversion above which we fully control. So when `timezone` differs from the device's zone, the raw cross-timezone instant for a bound is re-anchored onto the same calendar-day numbers under the device's timezone before being handed to `minDate`/`maxDate`, rather than passed through directly — otherwise the widget could gray out the wrong day relative to what was actually intended.
